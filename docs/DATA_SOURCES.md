# 数据源

本文档是本项目**最需要认真读**的一篇。它列出每份数据的来源、实测表现、
已知风险与排障方法。

**总原则：全部数据来自公开免费接口，不需要账号、API Key 或付费。**

## 2. 指数日线（新浪财经）

### 接口

```python
import akshare as ak
df = ak.stock_zh_index_daily(symbol="sh000688")   # 科创50
df = ak.stock_zh_index_daily(symbol="sz399006")   # 创业板指
df = ak.stock_zh_index_daily(symbol="sh000016")   # 上证50
```

格式：`sh` / `sz` + 6 位数字。

### 实测

| 指标 | 值 |
|---|---|
| 耗时 | 约 0.8 秒 |
| 返回行数（sh000688） | 1637 行 |
| 最新数据日 | 与交易日历一致 |
| 需要认证 | 否 |

### 已知风险

- **新浪会限流**。本项目默认重试 3 次、指数退避（0.5/1.5/4.0 秒）+ 30% 抖动。
- **东财接口在本机环境不可达**（`push2his` / `push2@@ 域名解析失败），
  因此本项目**只用新浪**，没有做东财回退。如果你的网络能访问东财，
  欢迎贡献一个回退数据源。
- 表头 BOM：pandas 2.x 读 `utf-8-sig` 不剥离 BOM，本项目在
  `store.read_csv_any` 里统一处理。

## 3. QVIX（1.optbbs.com）—— 最大的脆弱点

### 接口

```
http://1.optbbs.com/d/csv/d/k.csv
```

一个 87 列的 CSV 宽表，每行一个交易日，每 4 列对应一个品种的
（开、高、低、收）。日期格式形如 `2026/9/30`。
文件编码为 GBK。

本项目需要的列（**收盘**列，即每个品种的第 4 列）：

```python
QVIX_COLUMNS = {
    "kcb":       (82, 85),   # 科创50 期权  ← 科技板块用
    "cyb":       (70, 73),   # 创业板 期权   ← 科技板块用
    "50etf":     (62, 65),   # 上证50ETF 期权
    "300etf":    (34, 37),
    "500etf":    (54, 57),
    "100etf":    (38, 41),
    "1000index": (78, 81),
    "300index":  (2, 5),
    "50index":   (66, 69),
}
```

### 实测（多次抓取的真实数字）

| 指标 | 值 |
|---|---|
| 文件大小 | 913,900 字节（约 893 KB） |
| 行数 | 2,823 个交易日 |
| 首行 | 表头（1 行忽略） |
| **耗时** | **1.7 秒 ~ 123 秒，波动极大** |
| 有效数据比例 | 各列仅 23% ~ 34% 的单元格是数字 |

### ⚠️ 必须知道的四件事

**(1) 上游很慢，且不稳定。** 服务端带宽约 8~11 KB/s，且不支持压缩
（已验证：请求 `Accept-Encoding: gzip` 返回依然是 913,900 原始字节，
响应头无 `Content-Encoding`）。因此没有客户端优化空间。

本项目的应对：

- 单次读超时 150 秒（`timeout_qvix`）；
- 总预算 300 秒，含重试（`budget_qvix`），每次尝试的读超时会被
  剩余预算夹紧，避免无限等待；
- 超预算立即**降级用本地缓存**，并在输出中显式标注滞后几个交易日。

**(2) 大量单元格是 Excel 错误串。** 宽表里充满了 `#NUM!` 与 `0`。
实测各列数值占比只有 23%~34%。**这不是取错列的信号**，
是上游数据的固有特征（越靠后的品种越稀疏）。

一个重要的教训：我们最初用「数值占比 < 50% 就判为取错列」做断言，
结果**误杀**了完全正确的数据。现在的判据改成了：
列数断言 + 取值合理性断言 + 与本地缓存交叉校验。

**(3) 列号是硬编码的，这是最危险的失效模式。**
一旦上游调整列顺序，我们会**静默地**读到另一个品种的数据——
数值看起来完全正常（也是一个波动率指数），但含义全错。

三道防线：

| 防线 | 实现 | 拦什么 |
|---|---|---|
| 列数断言 | `assert_structure` | 上游删列 → 显式拒绝 |
| 合理性断言 | `assert_structure` | 中位数不在 3~150 / 出现非正值 / 跨度不足 180 天 → 拒绝 |
| **OHLC 结构不变量** | `_assert_ohlc_invariant` | 取到的 4 列不满足「开≤高、低≤高、低≤收≤高」→ 拒绝 |
| 缓存交叉校验（辅助） | cross_check_cache | 与本地缓存重叠日期的中位偏差超过典型日度波动的 4 倍（或超过 8 点）→ 拒绝新数据 |

**第三条（OHLC 结构不变量）才是最有效的一道。** 实测对 9/9 个正确窗口放行、
对 9/9 个错位窗口拒绝，两侧没有重叠。

**(4) 关于「上游会重算历史值」——此前的说法是错的，本处更正。**

本项目早期版本曾写下：「上游每次请求都会重算历史值，两次抓取的重叠日有 1%~2% 偏差，
科创50 中位数 30.4 vs 缓存 31.37」。**这个结论已被推翻，原因是我们自己取错了列。**

真相：

- 那个偏差就是**最低价（low）与收盘价（close）的差**，不是任何「重算」。
  交错列号整体错位一格后，每个品种取到的都是当日最低价，而 low 与 close
  只差约 2%，看上去完全正常。
- **上游并不重算历史值。** 相隔约 24 小时的两次完整下载**逐字节相同**。
- 更糟的是，缓存也是用同一个错误映射写入的，所以「新抓取 vs 缓存」的交叉校验
  比较的是同一种错误 —— 比值恒为 0，这道防线**完全失效**，还替错误数据背了书。

**教训：用同一份有缺陷的实现生成「基准」，再拿它校验自己，是无效校验。**
现在已经把主防线换成不依赖缓存的 OHLC 结构不变量（见上表第三条）。

因此：**给定同一份缓存，输出是可逐字节复现的**（算法确定性，由测试锁定）；
重新抓取时，只要上游没有真的改动历史行，结果也应一致。
需要严格引用时仍建议留档当时的 `data/cache/`。

**(5) 只有 HTTP，没有 HTTPS。** 端口 443 会立刻
`SSLError` 失败。因此传输是明文的。
**我们只从该站读取公开市场数据，不上传任何内容、不发送任何凭据**
（本来也没有凭据）。

### 已知风险清单

| 风险 | 严重度 | 现状 |
|---|---|---|
| 站点停服 | 高 | 无替代源；会导致 F 因子永久缺失（仍有即时口径可用） |
| 列顺序变更 | 高 | 三道防线拦截，但非 100% |
| 长时间超时 | 中 | 有预算上限，超时降级并显式标注 |
| 明文 HTTP | 低 | 只读公开数据，无凭据可泄露 |
| 数据质量问题 | 中 | 无法为上游背书，请自行交叉验证 |

## 4. 降级阶梯

程序在任何一步失败都不会崩溃，而是按下面的阶梯退让，**每一步都明确告知用户**：

| 情况 | 行为 | 退出码 |
|---|---|---|
| 正常 | 抓取 → 计算 → 输出，两个口径都是最新 | 0 |
| QVIX 未发布（正常滞后） | 完整口径停在上一交易日并标注滞后天数 | 2 |
| QVIX 抓取失败但有缓存 | 用缓存并标注滞后 | 2 |
| QVIX 完全缺失 | 只出即时口径 | 2 |
| 指数抓取失败但有缓存 | 用缓存并标注 | 2 |
| 指数完全不可用 | 跳过该标的并说明 | 2 |
| 全部标的都无读数 | 明确报「无数据」并给出下一步 | 3 |
| 依赖缺失 | 中文指引，不打印堆栈 | 4 |

**「静默降级」是本项目明确禁止的行为。** 见 [CONTRIBUTING.md](../CONTRIBUTING.md) 的硬性规则。

## 5. 排障

### 先跑自检

```bash
python -m techpanic --check
```

它会报告 Python 版本、akshare 版本、指数源是否可达、数据目录与配置位置。

### 看清单

`data/cache/_manifest.json` 记录了每份缓存的来源、行数、最后日期、
抓取时间、滞后天数与文件哈希：

```json
{
  "version": 1,
  "datasets": {
    "index_sh000688": {
      "rows": 1637,
      "last_date": "2026-10-08",
      "source": "sina",
      "fetched_at": "2026-10-09T10:15:22+08:00",
      "stale_trading_days": 0,
      "sha1": "2d502fd9ea8ea1589d8b8fdb3f3ea54c2787ff4d",
      "bytes": 92459
    }
  }
}
```

### 常见症状

| 症状 | 可能原因 | 处理 |
|---|---|---|
| 退出码 3，无缓存 | 无网络 / 数据源被墙 | 检查网络；配代理 |
| QVIX 反复超时 | 上游慢（正常） | 等一次成功后就会用缓存 |
| 完整口径突然缺失 | QVIX 解析被拒 | 看警告文字，通常是交叉校验失败 |
| 读数明显离谱 | 上游列结构变更 | 删除 `data/cache/qvix/` 重抓；若仍异常请开 Issue |
| 「使用本地缓存（滞后 N 天）」 | 抓取失败 | 检查网络；滞后值本身可用于判断缓存新鲜度 |

### 强制重抓

```bash
python -m techpanic --refresh
```

### 彻底重置

```bash
# Windows
rmdir /s /q data
# macOS / Linux
rm -rf data
```

## 6. 关于数据入仓的决定

本项目**不附带任何数据文件、数据快照或数据镜像**。原因：

1. **会过期。** 附带的数据会让人误以为是最新的，比没有更糟。
2. **会误导。** 使用者应该看到真实抓取链路是否可用，而不是被一份
   「永远能跑通」的样例数据麻痹。
3. **体积与许可。** 上游数据的再分发许可不明；不复分发最干净。

因此：**首次运行必须联网。** 没有网络且没有缓存时，程序会给出退出码 3
和明确的中文指引，不会假装成功。
